# DNS-AID agent discovery — open items

Captured 2026-09-11, mid-task. Nothing in this repo changed; both remaining
steps are clicks in two web dashboards. Verified state at capture time is in
each section, so re-run the checks before assuming it is still true.

## Who owns what

Three parties, and confusing them is what stalled this:

- **Netlify** serves HTTP and never touches DNS. Irrelevant to all of the below.
- **Cloudflare** is the DNS operator. It holds the zone, signs it, and is where
  the SVCB record goes.
- **Squarespace Domains** (IANA registrar 895, the migrated Google Domains
  estate) is the registrar. It is the only party that can publish a DS record
  into the `.dev` parent zone, because the registry accepts DS only over EPP
  from the sponsoring registrar. That is why the DS does not live with the
  nameserver.

## 1. Publish the SVCB record (not done)

`dig +short SVCB _index._agents.hamishburke.dev` returned NXDOMAIN at capture,
as did `_agents.`, `index._agents.`, `_index.agents.` and the doubled
`_index._agents.hamishburke.dev.hamishburke.dev`. It was never saved.

Cloudflare > DNS > Records > Add record, type **SVCB**:

| Field | Value |
|---|---|
| Name | `_index._agents` |
| TTL | 1 hour |
| Priority | `1` |
| Target | `hamishburke.dev` |
| Value / SvcParams | `alpn="h2,h3" port=443 mandatory=alpn,port` |

Zone-file equivalent, if the UI offers one combined content box:

```
_index._agents.hamishburke.dev. 3600 IN SVCB 1 hamishburke.dev. alpn="h2,h3" port=443 mandatory=alpn,port
```

Priority `1` is what makes this a ServiceMode record rather than AliasMode, and
ServiceMode is what the spec requires. Leave it DNS-only.

Cloudflare's "manually-added HTTPS records on proxied names are not served"
caveat does not apply: that is about HTTPS records on the proxied apex, and this
is an SVCB record on a separate unproxied name.

Deliberately omitted: `well-known=`, `cap=` and the draft's four other
SvcParamKeys. IANA has not assigned them, so publishing them means inventing a
private `keyNNNNN` number no consumer would recognise. When the draft gets real
key numbers the record gains a parameter rather than changing shape.

Verify:

```bash
dig +short SVCB _index._agents.hamishburke.dev
```

## 2. Anchor the DNSSEC chain (half done)

Cloudflare signing is **on**: DNSKEY and RRSIGs are being served. The parent has
**no DS**, so the chain is not anchored and validating resolvers still get
unauthenticated data. The registry states it exactly:

```
{"zoneSigned": true, "delegationSigned": false}
```

Squarespace > Domains > hamishburke.dev > DNS > DNSSEC > Add record. Four
fields, filled from Cloudflare > DNS > Settings > DNSSEC (which re-shows the
values any time):

| Squarespace field | Value |
|---|---|
| Key tag | the number Cloudflare labels Key Tag |
| Algorithm | `13` (ECDSAP256SHA256) |
| Digest type | `2` (SHA-256) |
| Digest | the long hex string |

The manual DS form only appears once the domain is on custom nameservers, which
it already is (`yichun`/`evangeline.ns.cloudflare.com`).

Verify, allowing up to an hour for `.dev` parent propagation:

```bash
dig +short DS hamishburke.dev
curl -s https://pubapi.registry.google/rdap/domain/hamishburke.dev | jq .secureDNS
```

`delegationSigned` must flip to `true`. Then run the end-to-end chain check at
https://dnssec-debugger.verisignlabs.com/hamishburke.dev — a mistyped digest
gives a *broken* chain, which is worse than no DNSSEC, because validating
resolvers will then refuse to resolve the domain at all.

## 3. Re-scan

```bash
curl -s -X POST https://isitagentready.com/api/scan \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://hamishburke.dev"}' | jq .checks.discoverability.dnsAid
```

Wants `"status": "pass"`. If it still fails with the record live, it may be
looking for the `_a2a._agents` label specifically, which would mean advertising
an A2A endpoint this site does not have. Do not publish that to satisfy a
scanner.

## Worth knowing before spending more time

DNS-AID is `draft-mozleywilliams-dnsop-dnsaid-02`, an individual Internet-Draft
with no formal standing, last updated 2026-05-27 and expiring 2026-11-28. The
site has no A2A or MCP agent; what it genuinely offers agents is the markdown
twins and `llms.txt`. The record above says only that, and says it truthfully.

An optional third piece was discussed and not started: serving
`/.well-known/agents/index.json` from `public/` listing the agent-readable
surfaces, so the DNS pointer resolves to an actual index. Not required by the
scanner.
